Chrome DevTools · a11y-debugging

Purpose. Debug a rendered page using Lighthouse findings, browser issues, the accessibility tree, keyboard input and measurements.

Useful contribution. A useful operational checklist for connecting a failing rendered element with semantic, focus and visual evidence. Inspect specific failing nodes and browser issues before choosing a repair.

Recommendation. Use selected debugging steps in a conditional web reference. Keep the host browser and verification recipe as the execution owners; do not require Chrome DevTools MCP everywhere.

Limits, conflicts and exact sources
  • Its navigation-first audit reloads the page. Preserve the failing dialog, authenticated session or unsaved state when that is the target; Addy explicitly addresses this choice.
  • The supplied contrast snippet is explicitly approximate. In our controlled probe, white text over a transparent background returned 21:1 although a white ancestor makes the displayed pair 1:1. It cannot establish a passing result for that case.
  • Its 48 px target recommendation is not the WCAG AA minimum. Bounding-box size alone does not establish the effective hit region, overlap or criterion exceptions.
  • The orphan-input snippet checks attribute presence, not the computed accessible name. A present aria-labelledby value can still point to missing or empty content.

License recorded. Apache-2.0 (repository license header checked; no source text or snippets incorporated).

Alireza Rezvani · a11y-audit

Purpose. Scan frontend source files, calculate color-pair contrast, prioritize repairs and produce an audit report.

Useful contribution. The report structure and simple color-pair calculation are useful examples. The supported positional contrast command correctly rejects #777777 on white for AA normal text.

Recommendation. Do not install this package or import its scanner into our completion checks. Its documented contract and implemented checks need correction first; the current skill already owns evidence-based findings and manual coverage.

Limits, conflicts and exact sources
  • The documented --format table, --report --output and --fg/--bg commands fail with exit code 2. The scanner actually accepts text/json formats; the contrast checker accepts positional colors.
  • Two isolated barriers pass the scanner: an unlabelled input with an id, and a click-only div with role=button. It also reports a wrapped, labelled input as critical and role=status without explicit aria-live as serious.
  • Its WCAG 2.2 reference calls Focus Appearance 2.4.11 AA. The published criterion is 2.4.13 AAA; 2.4.11 AA concerns focus not being entirely obscured.
  • The CI example reads violations and wcag, but the scanner emits findings and wcag_criterion. Its static regex checks cannot substantiate the entrypoint claim of finding every A/AA violation.

Proposed · not incorporated

Three small changes to consider

Keep the entrypoint generic. Place web-specific detail in accessibility/references/web.md, and use the verification tools already available in the host.

Trace the failing state to its component

Record the route, interaction and state; inspect failing rendered nodes, computed semantics and relevant browser issues; locate the responsible component or shared primitive. Use navigation audits for load behavior and a supported snapshot/current-state check when reloading would erase the target state. Rerun that same state after an authorized repair.

Why. The current skill already requires composed evidence and reruns. This makes the browser-to-source diagnosis and audit-mode choice explicit without adding a new workflow owner.

Make measurement limits concrete

Treat selector, attribute and rectangle snippets as candidate-finding tools. Confirm accessible names, effective hit regions and the actual composited contrast pair with suitable browser evidence; keep unsupported color formats or missing background information inconclusive.

Why. This prevents a plausible-looking number or attribute from becoming a false pass. Our broad evidence rule already says this; the proposed web detail gives a concrete stopping condition.

Check repeated help across the flow

Where the help mechanisms covered by WCAG 3.2.6 repeat across a set of pages, check their relative order under the same page variation and the user-initiated-change exception. The criterion does not require adding a new help mechanism.

Why. This is a useful coverage addition for multi-page tasks. Use the W3C criterion as authority, rather than inheriting a shorthand summary.

Problems reproduced in the supplied tools

Small counterexamples test specific claims. They do not measure overall audit quality or replace a browser and assistive-technology session.

Observed results from ten focused probes
ProbeObserved result and interpretation
unlabelled-input-with-idFalse negative: zero findings, exit 0; an id alone does not supply the missing label.

documented-table-formatInterface mismatch: documented table format rejected, exit 2.
documented-report-flagsInterface mismatch: documented report/output flags rejected, exit 2.
documented-contrast-flagsInterface mismatch: documented fg/bg flags rejected, exit 2.

The transparent-background result comes from a controlled computed-style stub, not a live page. Chrome's own snippet warns that it is approximate. The important limitation is that its output can look like a strong pass when composition is unknown.

Two positive controls also behaved as expected: the scanner caught a missing image alternative, and the contrast checker rejected the supported normal-text color pair. The conclusion is to avoid relying on the package as supplied, not that every function is unusable.
