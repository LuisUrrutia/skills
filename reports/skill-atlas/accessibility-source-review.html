Chrome DevTools · a11y-debugging

Purpose. Debug a rendered page using Lighthouse findings, browser issues, the accessibility tree, keyboard input and measurements.

Useful contribution. A useful operational checklist for connecting a failing rendered element with semantic, focus and visual evidence. Inspect specific failing nodes and browser issues before choosing a repair.

Recommendation. Keep only the useful gaps in the existing web reference: preserve the state being audited and recognize unresolved contrast measurements. Rendered-node inspection, computed names, hit regions and execution ownership are already covered locally.

Limits, conflicts and exact sources
  • Its navigation-first audit reloads the page. Preserve the failing dialog, authenticated session or unsaved state when that is the target; Addy explicitly addresses this choice.
  • The supplied contrast snippet is explicitly approximate. Claude also exercised it in the live T3 browser: #777 text on a white body returned 4.69:1 because the transparent element background was parsed as black; the displayed pair is 4.478:1 and fails normal-text AA. Unresolved backgrounds, alpha or modern color syntax cannot establish a passing measurement.
  • Its 48 px target recommendation is not the WCAG AA minimum. Bounding-box size alone does not establish the effective hit region, overlap or criterion exceptions.
  • The orphan-input snippet checks attribute presence, not the computed accessible name. A present aria-labelledby value can still point to missing or empty content.

License recorded. Apache-2.0 (repository license header checked; no source text or snippets incorporated).

  • https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/b2f522c8ba0fd2e00a679159b4aa5243de5f1b78/skills/a11y-debugging/SKILL.md

Purpose. Scan frontend source files, calculate color-pair contrast, prioritize repairs and produce an audit report.

Useful contribution. The supported positional contrast command correctly rejects #777777 on white for AA normal text. This working calculation does not establish that the scanner, documented CLI or CI examples form a reliable audit workflow.

Recommendation. Do not install this package or import its scanner into our completion checks. Its documented contract and implemented checks need correction first; the current skill already owns evidence-based findings and manual coverage.

Limits, conflicts and exact sources
  • The documented --format table, --report --output and --fg/--bg commands fail with exit code 2. The scanner actually accepts text/json formats; the contrast checker accepts positional colors.
  • Two isolated barriers pass the scanner: an unlabelled input with an id, and a click-only div with role=button. It also reports a wrapped, labelled input as critical and role=status without explicit aria-live as serious.
  • Its WCAG 2.2 reference calls Focus Appearance 2.4.11 AA. The published criterion is 2.4.13 AAA; 2.4.11 AA concerns focus not being entirely obscured.
  • The CI JSON reader expects violations and wcag, but the scanner emits findings and wcag_criterion. That reader misses six critical findings in the retained sample. The preceding scanner step can still fail the complete GitHub Actions job; the isolated reader result does not prove the whole workflow always passes. Static regex checks also cannot substantiate the promise of finding every A/AA violation.

Proposed · not incorporated

Three small changes to consider

Keep the entrypoint generic. Place web-specific detail in accessibility/references/web.md, and use the verification tools already available in the host.

Preserve the state being audited

A reload can erase a dialog, error or unsaved state. Choose a supported check that preserves or reconstructs the intended state, and confirm that state is still present when the check runs. Keep tool-specific audit mode names in the local verification recipe.

Why. Tracing a defect to its responsible component and rerunning it are already in the skill. The new detail should prevent an audit from silently checking a different state.

Resolve the displayed contrast pair

An element without its own opaque background can report a transparent computed background. Account for the displayed background, compositing, alpha and supported color syntax. A snippet that cannot resolve the pair yields an inconclusive measurement, not a pass.

Why. Computed names, effective hit regions and occlusion are already covered. Keep this addition specific to the demonstrated contrast failure.

Check consistency across pages

When a flow spans a set of pages, check the relative order of repeated navigation and applicable help mechanisms, and consistent identification of the same function, under WCAG 3.2.3, 3.2.4 and 3.2.6. Respect their scope and user-initiated changes. Consistent Help does not require adding help or showing it on every page.

Why. This checks a coherent part of the user flow. Adding only the criterion named by one donor would leave the purpose of the change unclear; the reference remains selective rather than a complete WCAG checklist.
