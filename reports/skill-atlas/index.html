CI/CD: decide what permits the next step

ci-cd-automation defines pipeline structure, required checks, artifact promotion, delivery criteria and recovery. It works across providers and languages. github-actions implements the GitHub-specific contract.

What it helps the agent decide

Which checks belong in CI, which evidence makes a release eligible, how stages depend on each other, and how the actual result will be observed. It starts from project commands and release requirements, then chooses the smallest adequate flow.

A service, a library and a mobile app need different delivery boundaries. The skill does not prescribe a staging cluster, a fixed coverage target or a manual approval for every product.

Why derive it

The sources contain useful decisions alongside provider templates, fixed thresholds and broad deployment policies. The derivation keeps the decision-making and assigns implementation to specialists.

Its central safeguard is traceability: a green PR, a successful build and a healthy release are different claims. Checks and approvals must apply to the candidate and artifact that actually advance.

TypeScript: keep the guarantees honest

typescript-best-practices supports implementation and review with a 534-word core. pstack is the primary source. The skill concentrates on decisions that a green compiler can conceal: invalid domain states, unvalidated data, mutable aliases, missing values and ignored promises.

Why derive it

pstack's strongest criterion is to strengthen a type when an operation needs the guarantee. Several source recipes need qualification: a numeric duration can be negative, a mutable non-empty tuple can become empty, and satisfies does not validate runtime input.

The local skill keeps that reasoning and corrects those assumptions. It preserves public contracts, useful optional fields and justified boundary assertions.

What stays outside

No syntax tutorial, advanced-type catalog, mandatory schema dependency, enum/interface preference or folder layout. Existing tooling owns enforceable style. Compiler and module guidance loads only when the task reaches that boundary.

design-code-structure, review-code-changes, error-handling and verify keep their responsibilities. A TypeScript file does not require every workflow.

    What project research should establish

    Start with the checkout, its commands, domain model, tests, and existing instructions. Use relevant available Notion, Confluence, Jira, GitHub, Linear, Slack, or other project sources to establish business rules, ownership, and rationale.

    Match the project before expanding searches. Fetch the deciding document or thread, follow approval and supersession links, and separate current implementation from approved intent and proposals. A closed ticket does not prove deployment.

    Result: concise instructions with verified commands, material constraints, and usable context pointers. Report inaccessible sources and unresolved decisions. Do not copy private discussions or customer details into a public repository.

    What workflow extraction should retain

    Follow the evidence behind a successful choice, including its exceptions. Reusable judgment belongs in a skill; a business rule belongs with the project; a personal preference keeps its intended scope; a deterministic check should use its existing tool when available.

    A missed skill invocation calls for a selection correction, not another copy of the same procedure. A one-off approval does not become permanent authority. Some lessons require no new instructions.

    Por qué coordinar las piezas después de elegirlas

    Si se instalan todas las skills solapadas

    1. Una petición activa varias descripciones demasiado amplias.
    2. Varias skills reclaman la misma fase.
    3. Compiten decisiones sobre borrador, rebase y cuándo detenerse.
    4. El agente dedica esfuerzo a reconciliar instrucciones.

    Riesgo deducido de las contradicciones de las fuentes; no es un resultado medido.

    La composición propuesta

    1. Tus reglas fijan alcance y autorización.
    2. work-mode selecciona la tarea y la siguiente fase.
    3. Cada operación tiene un responsable; las especialidades aportan criterios pertinentes.
    4. Cada fase devuelve evidencia y un estado de continuación.

Una petición explícita de implementación completa incluye implementar, verificar, abrir un PR en borrador y seguirlo hasta que esté preparado para integrar. Instalar una skill no concede permiso para publicar.

    1. Resolver alcance y estado de trabajo

      Identificar tarea, rama, base, cambios locales, autorización y tecnologías reales. Reutilizar un checkout adecuado. Delegar el ciclo de worktrees a worktrunk; en una sesión Orca, un cambio de destino exige la transferencia establecida y que el agente inicial se detenga.

    2. Investigar y elegir el plan mínimo útil

      Para un fallo, capturar el síntoma y contrastar causas. Para una funcionalidad, inspeccionar comportamiento cercano y modelar el estado importante. Escalar a alternativas de arquitectura solo ante una decisión relevante sin resolver.

    3. Cargar especialidades antes de decidir

      Detectar dependencias, tipos de archivo y comportamiento modificado. Consultar composición de React antes de fijar la API, y seguridad de Actions antes de escribir YAML. Revisar la selección cuando el diff introduzca otra preocupación.

    4. Implementar y demostrar el comportamiento

      Realizar un cambio coherente. Demostrar fallo y éxito con una prueba significativa cuando corresponda; ejecutar compilación y una comprobación de una ruta ajena al cambio. Las interfaces necesitan interacción real. Eliminar instrumentación temporal.

    5. Revisar, limpiar, guardar y publicar

      review-code-changes devuelve hallazgos con evidencia. El responsable los evalúa, corrige y elimina narración redundante sin borrar motivos útiles. Repite las comprobaciones afectadas. commit gestiona commits atómicos y pr la publicación y descripción verificadas.

    6. Continuar o devolver el resultado solicitado

      Una petición completa entra en pr-followup; una petición local termina con estado local verificado. Informar de evidencia exacta, requisitos pendientes y siguiente responsable. Una comprobación bloqueada nunca cuenta como superada.

    Cuándo merece la pena un worktree

    Crear o reutilizar otro checkout cuando haya escritores concurrentes independientes, cambios ajenos que preservar, experimentos que necesiten estado separado o una petición explícita. Para trabajo secuencial corriente, conservar el checkout adecuado. wt gestiona su ciclo de vida; el coordinador justifica la necesidad. No copiar el requisito universal de worktree, los restablecimientos destructivos ni los comandos que eluden la propiedad de Orca.

    Estado de continuación sugerido: alcance, checkout propio, rama y base, fase, especialidades activas, revisión exacta verificada, hallazgos aceptados o descartados y siguiente acción. Guardar referencias en lugar de duplicar informes largos.
