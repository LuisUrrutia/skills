# Focused review delegation

Read this when independent risk areas justify focused subagents. One coordinator
owns the declared review; workers investigate complementary questions. The
protocol remains the authority for findings and the report grammar.

## Select work from the risks

First inspect the complete diff, intent, path inventory, and relevant contracts.
Keep straightforward work in this context. Delegate when distinct consequential
questions need substantial independent tracing or domain knowledge, such as
authorization plus asynchronous resource lifetime, or a migration plus its API
compatibility. A large file alone does not justify another agent.

Choose the smallest useful set of assignments. Common facets include behavior
and contracts, security, state and concurrency, structure, performance, or test
validity. Combine overlapping questions. Load available domain skills through
the specialist router; do not invent installed skill names or universal language
rules. Keep requirements, overall coverage, and cross-facet interactions with
the coordinator. Dividing files alone can hide the contract between them.

Use the host's actual delegation mechanism, available model catalog, and capacity.
Honor the caller's model, effort, budget, and agent constraints. Separate contexts
on one model can investigate independently; role-play in this context is not a
subagent run. This skill grants no additional external-service or code-sharing
authority. If delegation is unavailable, continue the supported review directly
and disclose the missing independence; an explicitly required parallel review
remains unmet.

## Assign a bounded investigation

Give each worker:

- The exact comparison and source snapshot, intent, applicable requirements and
  standards, caller-owned seams, and relevant setup facts.
- One concrete risk question, the assigned changed paths and their JSON inventory,
  and permission to trace relevant surrounding code within the parent's boundary.
- This skill and protocol, its non-delegating worker role, permitted read-only
  checks, and a separate report and scratch destination.
- A requirement to return the canonical report validated against its assigned
  inventory. Coverage must name the facet actually examined and any limits.
  Zero findings and unresolved questions are valid results.

Keep first-pass workers independent of the implementer's reasoning and emerging
review conclusions. A later validation assignment may receive a candidate finding
with a request to test its decisive premise and strongest counterevidence.

Workers must not spawn agents, invoke `compare-solutions`, repair the product,
or publish feedback. They may use compatible specialist instructions directly.
Read-only workers can share a stable source snapshot; checks that mutate caches,
services, or other shared state need separate permitted resources or serialization.
An output filename alone does not isolate those effects.

Record actual task IDs, assigned facets and paths, snapshot, destinations, and
terminal states in a coordination note beside the canonical report. Launch within
the host's limits; collect every successful launch before integrating or returning.
A progress message or launch acknowledgement is not a completed review. Settle
or cancel remaining work before closing the run.

## Integrate evidence and coverage

Read every returned report, including Checks, Open questions, and Coverage.
Confirm its snapshot and validate its assigned inventory. Treat a missing,
malformed, failed, or unfinished report as incomplete work. A later failure cannot
be replaced by an earlier clean result. Investigate the affected facet directly,
retry when there is a concrete recoverable cause, or carry its coverage gap into
the final report; never count failure as zero findings.

Recheck each retained claim against source evidence or an allowed probe. Use a
fresh validation worker when a consequential disputed premise warrants it, within
the same budget; agreement between workers never bypasses validation. Preserve
supported minority findings, reject shared false positives, and use Open questions
when a missing premise decides whether the defect exists.

Merge duplicate causes while preserving distinct consequences. Check interactions
between facets and cover the remaining changed paths yourself. A path inspected
for security alone is not evidence that its behavior and requirements were fully
reviewed. Describe the actual combined coverage, including partial or unreadable
paths, and validate the final report against the original complete inventory.

Keep task bookkeeping in the coordination note; the user-facing report stays about
the change, evidence, actions, and limits. Use the entrypoint's normal delivery and
completion rules. A well-formed report or a completed set of workers does not prove
that every conclusion is correct.
