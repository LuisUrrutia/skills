# Explanations and channels

Read this when the reader needs an unfamiliar idea explained, an earlier
explanation failed, or a channel changes how the message should be delivered.
Use the relevant guidance; this is not a fixed output template.

## Make the explanation usable

Start from what this reader already knows. Explain the missing relationship,
mechanism, or consequence, then connect it to their question. Use a concrete
case when it reduces abstraction. Do not infer low intelligence from a request
for plain language or withhold technical detail an expert needs.

Define necessary terms close to their first use. Follow an available domain
glossary without importing irrelevant definitions. Stable naming matters more
than variety: one object should not acquire several aliases to avoid repetition.

Use an analogy only when it clarifies the relevant relationship. Explain a
material limit before the reader could use the analogy to make a wrong decision.
If a concrete example explains the mechanism directly, an analogy may add work.
Keep examples supplied for a rewrite exact in meaning; label new hypothetical
examples in an explanation and avoid presenting them as observed outcomes.

When the reader says the explanation did not help, change the route: use a smaller
case, show an intermediate step, or name a missing prerequisite. Repeating the
same jargon with more words rarely resolves the gap. Ask a focused question
when the point of confusion cannot be inferred; do not require a quiz.

Match form to the information. Prose explains a relationship; a list makes
parallel items or steps easier to scan; a table compares the same dimensions.
A diagram can explain a flow, boundary, or dependency. Use a visual when requested
or when it materially helps, with tools supported by the environment. Keep
meaningful labels and a text explanation so the message does not depend solely
on the image. Claim rendering or verification only when observed.

## Match the destination

- **Conversation:** answer the question directly and add the reasoning needed
  for this reader. Do not add an action or follow-up offer when none is useful.
  When the agent owns authorized work, do it instead of giving the user a new
  checklist to perform.
- **Slack or another team chat:** make the point, decision, or needed response
  easy to find. Include the context and source link recipients need without
  assuming they saw the agent conversation. Use threads or a longer document
  when detail warrants it, not a universal one-line limit.
- **Email:** put the purpose early. Make any ask and its relevant timing explicit
  from known facts; do not invent deadlines, commitments, approval by silence,
  or reasons for a decision. Preserve appropriate greetings and relationship tone.
- **Status or decision note:** distinguish completed work, evidence, unresolved
  uncertainty, and the actual next actor. Give enough reason to assess a decision;
  do not turn a proposal or attempted check into a completed result.
- **Public or personal writing:** match the requested voice and genre. Keep
  legitimate emotion, humor, narrative, or rhetorical emphasis. Removing stock
  phrasing must not flatten the author's personality into corporate prose.

Prepare the content for the destination's audience. Private source details are
not automatically suitable for broader distribution. Use only relevant authorized
context, and report a material audience or confidentiality conflict instead of
silently exposing it. Channel adaptation does not itself authorize external sends.
